# Итоговый отчет по оптимизации сетевой конфигурации VPN-серверов

Я собрал профиль железа серверов (на всех по 1 ядру и 1-2 ГБ ОЗУ) и успешно применил единую унифицированную сетевую конфигурацию для всех трех VPS. Это гарантирует, что трафик будет предсказуемо маршрутизироваться во всей цепочке (Relay -> Exit Node) без "затыков" ни на одной из сторон.

---

### Анализ "До"

1.  **VK Cloud (Москва — 1 GB RAM):** Был самым слабым звеном (Bottleneck). Использовал стандартный устаревший `cubic` и отбраковщик пакетов `fq_codel`. Максимальный размер TCP-окна (буфера) составлял крошечные **~212 КБ**. 
2.  **HostVDS (Финляндия — 2 GB RAM):** BBR был включен, но TCP-буферы оставались зажатыми на тех же **~212 КБ**.
3.  **62YUN (Германия — 1 GB RAM):** Имел неплохой тюнинг (TCP-окно на ~12 МБ), но настройки немного отличались от оптимальных для VPN-туннелирования (например, отсутствовали жесткие file descriptors для всех юзеров).

---

### Что было изменено (Состояние "После") 🚀

Я создал и применил два глобальных конфигурационных файла на всех системах: `99-vpn.conf` для ядра (sysctl) и файл лимитов для файловых дескрипторов. 

Вот конкретные изменения и зачем они нужны:

#### 1. Алгоритм контроля перегрузки: `bbr` + `fq`
*   *Было (на VK Cloud):* `cubic` (сильно режет скорость при потерях пакетов от 1%, что характерно для мобильных сетей).
*   *Стало:* `net.ipv4.tcp_congestion_control = bbr` (у всех). BBR оценивает не потери пакетов, а реальную пропускную способность, поэтому скорость проксирования (особенно к клиентам 4G/LTE в Москве) вырастет в разы.

#### 2. Расширение TCP-буферов: До 16 Мегабайт
*   *Было:* ~212 KB `rmem_max` / `wmem_max`
*   *Стало:* **16 MB** (`16777216`).
*   *Почему:* Чем больше RTT (пинг) между серверами, тем шире нужен буфер для заполнения канала (Bandwidth-Delay Product). Чтобы передавать гигабайты видео из Германии через Москву без лагов, 212 КБ недостаточно. 16 МБ идеально подходит под 1-2 ГБ оперативной памяти серверов (мы не вызовем OOM killer).

#### 3. Мощность очередей SYN Backlog
*   *Было:* 128 соединений (быстро уходит в отказ при микро-сканированиях или переподключениях).
*   *Стало:* **8192** (для SYN-очереди) и **10000** (для сетевых устройств). 
*   *Почему:* Серверы смогут выдерживать кратковременные всплески подключений сотен VPN-клиентов (например, после падения сети или обновления).

#### 4. Обход "Черных дыр" (MTU Probing)
*   *Было:* 0 (Отключено) на РФ и Финляндии.
*   *Стало:* `net.ipv4.tcp_mtu_probing = 1`
*   *Почему:* При шифровании Reality/WireGuard меняется размер пакета. Раньше, если встречался промежуточный узел, дропающий фрагментированные пакеты, соединение просто висло ("черная дыра"). Теперь ядро само определит оптимальный размер MTU для таких участков.

#### 5. Системные лимиты (File Descriptors)
*   *Было:* Soft limit 1024 открытых файлов (что для Xray с сотнями клиентов критически мало).
*   *Стало:* Soft/Hard limit повышен до **1,048,576** (`ulimit -n`). 
*   *Почему:* Предотвращает ошибку "Too many open files", которая "молча" кладет прокси-сервер при длительном Uptime.

### Итог
Теперь на всех серверах ядро Linux настроено "сообща". VK-Relay будет принимать потоки от клиентов большими 16МБ кусками через BBR и в том же темпе "пробивать" их в Финляндию без задержек. Улучшение скажется на отзывчивости (TTFB) и максимальной скорости скачивания торрентов/видео.
